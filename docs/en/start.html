Get started · Node, wallet, local testnet

Fetch the code, and run it

Everything below was executed on 27 July 2026 on a Windows machine, in the order it is written. No command here was copied from a document: they are transcribed from a real run, all the way to a received payment.

▲

Unaudited prototype, no value. There is no public Obscura chain, no faucet and no explorer — by decision, not by omission. What you set up here is a chain of your own, on your own machine.

Step 0

Fetch the source

The repository is public, licensed MIT or Apache-2.0, at your option.

git
git clone https://github.com/nailiwalid-del/obscura.git
cd obscura

Or, without git, an archive of the current state:

archive
curl -L -o obscura.tar.gz \
  https://github.com/nailiwalid-del/obscura/archive/refs/heads/master.tar.gz
Why there is no binary to download

No binary release has been published to date — so this page does not offer you one. The signed-release machinery does exist in the repository (deploiement/), but publishing a release and opening a chain are deliberate operator gestures, not by-products of a website. The verification procedure is described further down, for the day it becomes relevant.

Step 1

Build

Rust 1.87 minimum (2021 edition). Nothing else is required.

build
cargo build --release -p node --bins

Four binaries appear in target/release/:

BinaryRole
obscura-geneseBuilds a chain's initial block: allocations and, optionally, the list of authorities.
obscura-nodeThe node: networking, mempool, validation, and — by decision — block production and archiving.
obscura-walletThe wallet: create, synchronise, check balance, pay, consolidate.
obscura-demoA self-contained demonstration: two real nodes and one transaction, in a single command.
--release is not an optional optimisation

STARK proofs are gated on building in release. In debug the proving path is unavailable: it is not “slower”, it is absent.

Path A

Check that it works, in one command

Two real nodes, one transaction issued and propagated. Nothing to configure.

demo
cargo run --release --bin obscura-demo

That is the shortest answer to “does this thing actually work”. To set up a chain of your own, move on to the next path.

Path B

A local testnet, end to end

One machine, an open chain, a wallet that receives and then pays. This is the only path you can follow alone — joining a federation requires an invitation.

  1. Create a wallet and read its address

    The passphrase is requested interactively, or supplied via the OBSCURA_WALLET_PHRASE environment variable.

    wallet
    obscura-wallet creer   --fichier mon.wallet
obscura-wallet adresse --fichier mon.wallet

    The address is roughly 2,500 characters long. That is not a bug: it carries post-quantum keys, which are bulky.

  2. Build the genesis, allocating the initial supply to yourself

    Without --autorite, the chain is open: any node started with --sceller will produce blocks on it. That is what you want locally, and never on a public network.

    genesis
    # replace obs1… with the address printed in the previous step
obscura-genese --sortie genese.bin --allocation obs1…:1000000

    The command prints the chain's full identifier (128 hexadecimal characters). That is the anchor: with several operators, it is compared in full before anyone starts. The short form is only a visual cue.

  3. Start the node — sealer and archivist

    --archiver retains history. With no archivist on the network, no wallet can bootstrap.

    node
    obscura-node --ecoute 0.0.0.0:9333 --genese genese.bin \
             --donnees ./donnees --sceller 1000 --archiver

    At startup it states exactly what it is (log messages are in French):

    observed output
    INFO   archivage ACTIVÉ — 1 sorties conservées (≈1 Kio)
INFO   genèse c2ca4023f3892057…70c9ee08 (1 émissions) — tête courante c2ca4023f3892057
INFO   scellement ACTIVÉ toutes les 1000 ms
AVERT  chaîne OUVERTE, aucune élection de producteur : ordre convenu, pas défendu
INFO   écoute sur 0.0.0.0:9333

  4. Synchronise, then read the balance

    The wallet receives: it replays history and recognises its own notes in it.

    sync
    obscura-wallet synchroniser --fichier mon.wallet --noeud 127.0.0.1:9333
obscura-wallet solde        --fichier mon.wallet

    Note how the result is phrased: “up to date according to this node”. Without a witness, an omission on its part would stay invisible — see below.

  5. Pay

    payment
    obscura-wallet envoyer --fichier mon.wallet --a obs1…recipient \
                       --montant 300 --noeud 127.0.0.1:9333

    On the test machine the proof took 0.7 s for 85.6 KiB, in 1-in / 2-out shape.

    Change does not come back immediately

    Its index in the consensus tree does not exist until the transaction is sealed. It reappears at the next synchroniser — it is encrypted to you, so it is recognised on scan. The verified run: balance 1,000,000, send 300, then 999,700 after resynchronising, and 300 at the recipient.

Understand before typing

Three options that are decisions

They are off by default, and that is not a configuration oversight.

--sceller — producing blocks

Off by default: producing blocks is an operator's decision. On a chain with authorities, a node that is not one refuses to seal and says so. Reducing a committee to three members or fewer sacrifices fault tolerance — the quorum then equals the whole committee, and no absence is tolerated.

--archiver — serving history

Off by default, because it is a costly role: roughly 1.4 KiB per output, never pruned. A node that does not enable it remains perfectly valid, but cannot bootstrap any wallet.

--noeud-synchro and --temoin — two different leaks

Synchronising and then paying through the same node identifies you as the sender: a Dandelion++ relay has never just synchronised. Use --noeud-synchro so the two differ — ideally on different networks. The tool warns you when they coincide.

--temoin addresses a different problem: the node serving history can lie by omission. The witness queries a second node at the same height and compares roots; a disagreement halts everything before application. It is only worth anything if chosen independently, and it does not say which of the two is lying.

Beyond local

Joining a federation

By invitation. There is no public bootnode, no directory, and no button.

Each prospective sealer publishes the public key of their node. Nobody sends their identity file — it holds the secret.

identity
obscura-node --identite --donnees ./donnees

The resulting key goes to whoever builds the genesis, who burns it in with --autorite-hex. Peer addresses are exchanged out of band, then:

federated node
obscura-node --ecoute 0.0.0.0:9333 --pair <peer_address> \
             --genese genese.bin --donnees ./donnees
Before anyone starts, with several operators

Compare the full anchor (128 hexadecimal characters) between operators. Two nodes booted on different genesis blocks reject all of each other's blocks, and nothing in the error messages points at the cause.

When the day comes

Verifying a signed release

No release has been published to date. The procedure is described here so it is known in advance, not because it applies today.

The repository carries the release public key (deploiement/release.pub) and the verification script. Signatures are minisign.

verification
./deploiement/verifier-release.sh <archive> <signature>

A release key fetched from the same place as the archive proves nothing. The day a release exists, compare the key against an independent source.

Check for yourself

Running the test suite

tests
# CONSENSUS surface only: monolith, ProvedTx, proved ledger
cargo test --release

# plus transparent dev mode and standalone sub-circuits
cargo test --release --all-features

By default only the consensus surface is compiled. Development paths live behind features that are off by default, so they are not mistaken for the consensus: the transparent ledger is explicitly non-private, and has no business in a security evaluation.
